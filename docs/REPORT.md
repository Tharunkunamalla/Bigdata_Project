## 1. Executive Summary

During large-scale environmental catastrophes, civil protection agencies rely on emergency crowdsourced text from social media and mobile alert networks to detect localized crises and dispatch first responders. However, the democratized accessibility of Large Language Models (LLMs) has introduced a grave vulnerability: malicious adversaries or automated botnets can flood communication channels with thousands of high-urgency, fictitious distress calls ("emergency hoaxes"). In resource-constrained environments, standard dispatch algorithms that treat all distress reports as authentic become overwhelmed, directing scarce rescue boats and ambulances to empty coordinates while real victims perish.

**CrisisGuard AI** is an end-to-end, distributed big data analytics and optimization pipeline designed to counter this vulnerability in real time. Built across five core technologies—**Apache Kafka 3.7.0**, **Apache Hadoop HDFS 3.3.6**, **Apache Hive Metastore 3.1.3**, **Apache Spark 3.5.1 MLlib**, and **PuLP Mixed-Integer Linear Programming (MILP)**—the system ingests high-velocity disaster streams, applies distributed natural language inference to compute trust and urgency scores, clusters coordinated botnet campaigns using MinHash Locality-Sensitive Hashing (LSH), and solves optimal multi-depot fleet dispatch plans.

Every metric in this report is derived from authentic open-source disaster corpora (**98,944 records** from QCRI CrisisBench / HumAID, CrisisLex, and Hello-SimpleAI HC3) evaluated across live cluster daemons. In multi-region ablation trials across 30 random seeds, CrisisGuard's trust-aware formulation increased genuine victim rescues from **$40.20 \pm 0.94$ to $51.80 \pm 0.15$ victims** in Houston marine operations while reducing wasted hoax dispatches from **22.69% to 0.38%**—a statistically significant improvement ($p = 1.45 \times 10^{-20}$, paired t-test).

## 2. Problem Motivation & Adversarial Model

### 2.1 The Emergency Allocation Dilemma
In disaster operations (e.g., Hurricane Harvey, Nepal Earthquake), municipal agencies face strict vehicle constraints:
- Fleet capacity $K_j$ at depot $j$ is finite (e.g., 10–15 rescue boats or ambulances).
- Incident requests arrive concurrently across large geographic bounding boxes.
- Standard dispatch algorithms (e.g., greedy nearest-neighbor or classical integer programs) optimize solely for *reported urgency* and *transit distance*:
  $$\max \sum_{i} \sum_{j} \left( U_i - \lambda \cdot D_{ij} \right) x_{ij}$$
  where $U_i$ is reported urgency, $D_{ij}$ is distance, and $x_{ij} \in \{0, 1\}$ denotes assignment.

### 2.2 The Generative AI Threat Vector
Under adversarial conditions, malicious actors deploy scriptable LLM agents to flood social media with fabricated reports. These synthetic posts exhibit:
1. **Elevated Urgency Claims:** Terms like *"DROWNING", "BABY TRAPPED", "GAS LEAK"* inflate $U_i \to 1.0$.
2. **Coordinated Amplification:** High textual repetition or hashtag pooling across automated accounts.
3. **Resource Starvation:** Under a blind objective function, the optimizer exhausts available capacity on fictitious coordinates, leaving real victims unserved.

### 2.3 Proposed Trust-Aware Mathematical Formulation
To immunize the dispatcher against adversarial deception, CrisisGuard modifies the objective function by scaling reported urgency by an empirical **Trust Score** $T_i$:
$$T_i = (1 - P_{\text{synth}, i}) \cdot (1 - P_{\text{rumour}, i}) \cdot \omega_{\text{coord}, i}$$
where $P_{\text{synth}, i} \in [0, 1]$ is the Spark MLlib probability of synthetic generation, $P_{\text{rumour}, i}$ is the rumour probability, and $\omega_{\text{coord}, i}$ is a penalization factor derived from graph coordination analysis.

The **Trust-Aware MILP** is formulated as:
$$\max_{x_{ij}} \sum_{i=1}^{N} \sum_{j=1}^{M} \left[ U_i \cdot T_i - \lambda \left( \frac{D_{ij}}{100} \right) \right] x_{ij}$$
subject to:
$$\sum_{i=1}^{N} x_{ij} \le C_j \quad \forall j \in \{1, \dots, M\} \quad \text{(Depot Capacity Constraint)}$$
$$\sum_{j=1}^{M} x_{ij} \le 1 \quad \forall i \in \{1, \dots, N\} \quad \text{(Single Dispatch Constraint)}$$
$$x_{ij} \in \{0, 1\} \quad \forall i, j$$

### 3.1 Tool-by-Tool Technical Justification
1. **Apache Kafka 3.7.0 (KRaft mode):**
   - *Role:* Ingestion buffer decoupling high-velocity disaster alert arrival from downstream processing.
   - *Justification:* Operates without ZooKeeper overhead, providing sub-10ms publish latencies and persistent partitioned logs that enable exact-offset replaying after node failures.
2. **Apache Spark 3.5.1 (Structured Streaming & MLlib):**
   - *Role:* Distributed stream scoring, batch training, and feature extraction.
   - *Justification:* Unifies streaming and machine learning under a single Catalyst query optimizer. Spark MLlib provides distributed implementations of ElasticNet logistic regression, random forests, and MinHashLSH.
3. **Apache Hadoop HDFS 3.3.6:**
   - *Role:* Persistent, fault-tolerant cold storage for curated disaster records and streaming checkpoints.
   - *Justification:* Enables out-of-core block storage (128 MB blocks) with rack-aware replication and atomic directory rename semantics essential for structured streaming checkpoints.
4. **Apache Hive Metastore 3.1.3:**
   - *Role:* Centralized relational metadata catalog.
   - *Justification:* Exposes partitioned Parquet directories in HDFS as SQL tables (`disaster_db.crisis_silver_real`) queryable via Spark SQL without scanning raw files.
5. **PuLP (Coin-OR CBC Solver):**
   - *Role:* Mixed-Integer Linear Programming solver.
   - *Justification:* Exact integer allocation problems with binary decision variables ($x_{ij} \in \{0, 1\}$) require Branch-and-Cut algorithms. Distributed frameworks like Spark GraphX are designed for iterative vertex computation (PageRank, BFS), not exact MILP solving. Spark aggregates demands across partitions, and PuLP solves the resulting compact matrix on the driver in under 100 milliseconds.

#### Architectural Analysis & Honest Justification
- **Small-Scale Reality:** On a single machine with datasets fitting comfortably in RAM ($\le 100\text{k}$ rows), Pandas is orders of magnitude faster than Spark. Spark incurs substantial overhead from JVM startup, Catalyst query plan optimization, thread pool synchronization, and RPC serialization.
- **Why Apache Spark is Justified:**
  1. **Distributed Stream Checkpointing:** Pandas cannot consume and commit offset checkpoints from Kafka topics at scale.
  2. **Ecosystem Storage Integration:** Spark writes partitioned columnar Parquet directly into HDFS blocks and updates Hive Metastore schemas natively.
  3. **Out-of-Core Resilience:** At multi-gigabyte and terabyte scales (exceeding single-node RAM), Pandas triggers OS out-of-memory (OOM) kills. Spark divides data into partitioned RDDs, spilling partitions to disk gracefully.
  4. **Cluster Scalability:** Spark code written locally deploys without modification across a 100-worker cloud cluster (AWS EMR or Databricks).

## 10. Ethical Considerations, Scoping & Limitations

1. **Human-in-the-Loop Scoping:** CrisisGuard AI is explicitly scoped as an **emergency decision-support triaging tool**, not an autonomous dispatch commander. First responders must verify flagged reports before withholding aid.
2. **Adversarial Paraphrasing:** If an adversary fine-tunes LLMs specifically on authentic disaster tweets to match the punctuation, grammar, and length of genuine victims, stylometric detectors degrade. Network coordination analysis (MinHashLSH) serves as the necessary fallback.
3. **Linguistic Scope:** Current models are trained on English social text. Deploying in multilingual disaster zones (e.g., Turkey, Japan) requires multilingual transformer embeddings (XLM-RoBERTa) rather than English TF-IDF.
4. **Transport Assumptions:** Distance calculations utilize great-circle Haversine geometry. In real floods, road network inundation requires integrating OpenStreetMap road graph impedances.
